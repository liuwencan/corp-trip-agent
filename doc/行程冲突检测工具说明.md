# 行程冲突检测工具说明

## 为什么要检测行程冲突

出差申请创建前，如果只校验字段和日期格式，系统无法发现申请人已经有其他有效行程。用户可能在相同日期重复申请、同一时间段被安排到不同城市，或前后两段行程之间没有足够时间完成跨城移动。

这些情况会造成重复审批、行程无法执行、错过航班或高铁，也会让审批人和申请人依据不完整信息作出决定。冲突检测在创建前读取当前用户已有的有效申请，说明冲突对应的申请单、原因和建议，交由用户决策是否调整时间或继续。

## 检测流程

1. 管理智能体先收集拟申请的出发城市、目的地、出发日期和返回日期。
2. 调用 `check_trip_schedule_conflicts`。当前登录用户从 Agent 会话上下文读取，不接受模型传入的用户 ID。
3. 工具校验城市和日期，要求日期格式为 `YYYY-MM-DD`，并确认出发日期不晚于返回日期。
4. 服务按当前用户查询状态为 `DRAFT`、`SUBMITTED` 或 `APPROVED` 的已有申请。查询窗口在拟申请日期前后各扩展一天，以便检查相邻日衔接。
5. 工具逐条对比路线和日期，生成冲突明细，按 `HIGH`、`MEDIUM`、`LOW` 排序后返回 JSON。
6. 智能体读取每条冲突的 `type`、`severity`、`description` 和 `suggestion`，向用户解释原因并询问是否调整日期或继续。

`REJECTED`、`COMPLETED` 和 `CANCELLED` 申请不参与检测。日期按首尾均包含处理；同一天结束和另一段行程同一天开始时，会优先检查交通衔接。

## 四类冲突

### 1. 同路线日期重叠

类型为 `TIME_OVERLAP_SAME_CITY`，严重级别为 `LOW`。当已有申请和拟申请的出发城市、目的地分别相同，且日期区间相交时，工具将其视为可能的重复申请。

城市名会去除首尾空格、忽略大小写和末尾的“市”，因此“上海”和“上海市”会被视为相同。日期交集会写入原因，例如“日期在 2026-11-10 至 2026-11-12 重叠”。建议核对是否重复申请；如果确为不同事项，用户知情后可以决定继续。

### 2. 跨城日期重叠

类型为 `TIME_OVERLAP_DIFF_CITY`，严重级别为 `HIGH`。当两条申请日期区间相交，但出发城市或目的地不同，工具认为用户可能需要在重叠期间同时身处不同城市。

原因会列出已有行程、本次拟申请路线和重叠日期，并建议调整本次申请时间或先修改、取消已有申请。如果两条路线方向相反，例如已有“北京 -> 上海”、拟申请“上海 -> 北京”，原因会补充提示可能是同一趟往返被拆成两张申请，供用户核实。

### 3. 同日跨城衔接

类型为 `TRANSIT_TOO_TIGHT`。当已有行程结束日与拟申请出发日相同，或拟申请返回日与已有行程出发日相同，工具估算当天需要完成的城市间交通时间。

- 同城衔接（估算为 0 分钟）：不报告冲突。
- 估算时间不超过 8 小时：报告 `MEDIUM`，提示衔接偏紧并建议选择较早班次、预留缓冲。
- 超过 8 小时且不超过 24 小时：报告 `MEDIUM`，提示衔接非常紧张，建议改为次日或调整路线。
- 超过 24 小时：报告 `HIGH`，提示当天超出可行范围，建议至少延后一天或调整出发城市。

两条申请都是同一天的单日行程时，不按同日衔接处理，转由日期重叠规则判断。

### 4. 相邻日跨城路径断裂

类型为 `DISCONNECTED_ROUTE`，严重级别为 `MEDIUM`。当一条行程结束后的次日需要从另一座城市开始下一段行程时，工具估算结束城市到下一段出发城市的交通时间。

- 两段在同一城市衔接：不报告冲突。
- 估算时间不超过 8 小时：认为一天足以衔接，不报告冲突。
- 超过 8 小时：报告 `MEDIUM`，说明城市、日期和估算交通时间，并建议增加缓冲或调整一段行程的日期、出发城市。

该规则会检查“已有行程 -> 拟申请”和“拟申请 -> 已有行程”两个方向。

## 城市交通时长估算

估算由 `CityTransitTimeService` 执行，单位为分钟，配置文件为 `src/main/resources/config/city-tier.yml`，配置前缀是 `corp-trip.policy`。

计算顺序如下：

1. 城市相同返回 `0`。
2. 优先读取 `city-pair-minutes` 中配置的城市对耗时。配置按方向无关处理，例如“北京-上海”同时适用于“上海-北京”。
3. 未配置城市对时，按两地中等级较低的一方估算：一线或新一线为 `270` 分钟，涉及二线为 `300` 分钟，涉及其他或未知城市为 `360` 分钟。
4. 城市名称为空时按其他城市估算，即 `360` 分钟，并记录警告日志。

这是一种基于配置和城市等级的保守估算，配置意图覆盖通勤、候车/候机、在途和离站时间，不是实时航班、铁路或道路查询。当前配置的城市对估值最高为 390 分钟，城市等级兜底最高为 360 分钟，因此按现有配置，同日衔接会落在 `MEDIUM` 范围；`HIGH` 的 24 小时阈值用于未来配置出现极长交通估值时兜底。相邻日衔接当前配置下不会超过 8 小时阈值。

配置文件无法读取时，服务记录错误并使用空城市列表和空城市对映射，后续走未知城市 `360` 分钟估算。无效的城市对配置会被忽略并记录日志。已有申请的日期为空、格式错误或出发晚于返回时，该条申请会记录警告并跳过，不会阻断其他行程的检测。

## 返回给模型的 JSON

成功检查时返回以下结构。`total_conflicts` 等于 `conflicts` 数组长度；同一已有申请在本次检查中只产生一个冲突项。

```json
{
  "has_conflict": true,
  "total_conflicts": 1,
  "conflicts": [
    {
      "type": "TIME_OVERLAP_DIFF_CITY",
      "severity": "HIGH",
      "order_id": "existing-order-id",
      "order_summary": "北京 -> 上海，2026-11-10 ~ 2026-11-12（SUBMITTED）",
      "description": "已有行程与本次行程在重叠日期内路线不同，无法同时身处两地。",
      "suggestion": "调整本次申请的出发或返回日期以避开重叠区间，或先修改、取消已有申请。"
    }
  ],
  "summary": "命中 1 条冲突（HIGH=1, MEDIUM=0, LOW=0），请逐条阅读冲突原因和建议。"
}
```

`type` 取值为：`TIME_OVERLAP_SAME_CITY`、`TIME_OVERLAP_DIFF_CITY`、`TRANSIT_TOO_TIGHT`、`DISCONNECTED_ROUTE`。严重级别为 `HIGH`、`MEDIUM`、`LOW`，结果按级别从高到低排序。

参数错误或查询失败时，工具仍返回 JSON，不向模型抛出异常。失败结构额外包含 `success: false` 和 `error_code`，`summary` 会说明失败原因。模型必须将此类结果解释为“检查未完成”，不能把 `has_conflict: false` 当作“确认无冲突”，也不能继续创建申请。

无冲突时返回 `has_conflict: false`、`total_conflicts: 0`、空 `conflicts` 数组，以及说明已检查路线和日期的 `summary`。

## 创建保护与用户决策

冲突检测工具负责检查并提供建议，不直接创建或修改申请。管理智能体必须在创建前调用检测工具；发现冲突后向用户逐条说明已有申请、冲突原因、严重级别和建议，并等待用户明确选择。

创建工具会在写入前再次检查严格日期重叠：存在重叠且没有 `confirmConflict=true` 时拒绝创建。只有智能体确认用户已了解冲突并明确选择继续，才可以传入该标记。相邻日交通衔接问题由预检工具报告，创建工具的二次检查不重新评估相邻日交通，因此智能体必须遵循预检结果和用户确认规则。

## 不检测的影响

如果没有这项检测，系统只能确认申请字段和日期格式有效，无法及时发现：

- 同路线、同时间重复申请，造成重复审批和后续处理。
- 用户在重叠日期被安排到不同城市，导致申请计划在现实中无法同时执行。
- 同日跨城衔接时间过短，产生赶不上航班、高铁或其他交通的风险。
- 相邻日行程之间城市路线不连贯，留给跨城移动的时间不足。

冲突检测不会替用户判断是否必须取消申请，也不替代审批或实时交通查询；它将可核实的已有申请和估算风险交给用户决策。缺少检测时，这些风险只能依赖用户或审批人事后发现，可能导致申请反复修改、审批返工和实际出行受阻。
