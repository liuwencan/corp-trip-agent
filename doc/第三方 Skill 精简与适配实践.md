# 第三方 Skill 精简与适配实践

## 背景

第三方 Skill 通常面向通用用户和更广泛的产品场景，提供完整的意图识别、服务路由、工具调用、认证说明和示例。项目直接接入时，如果不检查其能力边界，Skill 可能会引导 Agent 使用本项目并不支持或不希望开放的功能，也可能带入与项目身份体系不一致的操作说明。

本项目接入途牛 `tuniu-cli` Skill 时，对其内容进行了面向企业内部差旅的适配。本文记录精简前后的范围、原因和可复用的检查方法。

## 精简前的内容

精简前的途牛 Skill 是面向 C 端旅行服务的统一入口，覆盖多种旅行产品：

- 国内和国际机票。
- 酒店住宿。
- 火车票、高铁和动车。
- 景点门票。
- 邮轮和游轮。
- 跟团、自助游、自驾游等度假产品。
- 机酒、酒火等多类资源的组合预订。

主文件根据用户意图将请求路由到不同服务，并引用各产品的详细说明。参考目录中既有企业差旅需要的酒店、航班和火车文档，也有门票、邮轮、度假和组合预订文档。认证说明默认先检查 OAuth 接入源，优先采用 OAuth，API Key 只是兜底方式。

## 为什么精简

CorpTripAgent 面向企业内部差旅。当前明确需要的出行资源是住宿酒店、国内或国际航班，以及火车、高铁和动车。旅游消费类产品和多资源打包预订不属于行程规划 Agent 的职责。

保留超出业务范围的意图和参考文档，会扩大模型可选择的工具空间。面对“出差顺便游玩”“去某地”等表达时，模型可能将需求误判为度假线路或门票搜索；多份无关工具说明也会增加上下文内容，给意图路由和工具选择带来不必要的噪声。

认证方式也需要符合项目的多用户模型。每个应用用户使用自己的途牛 API Key，项目 Hook 根据当前用户处理鉴权。让 Skill 默认执行 OAuth 登录或检查本机 OAuth 状态，会把 Agent 引向与应用用户隔离机制不一致的凭证路径。

## 精简后的范围

| 内容 | 处理方式 | 保留原因 |
|---|---|---|
| 酒店住宿 | 保留 `hotel` 及 `hotel.md` | 企业差旅住宿需求 |
| 国内航班 | 保留 `flight` 及 `flight.md` | 国内出行方式 |
| 国际航班 | 保留 `intelflight` 及 `intelflight.md` | 国际出行方式；保留按航线判断服务的规则 |
| 火车、高铁、动车 | 保留 `train` 及 `train.md` | 企业差旅出行方式 |
| 门票 | 删除相关路由、工具链路和 `ticket.md` | 属于旅游消费场景 |
| 邮轮 | 删除相关路由、工具链路和 `cruise.md` | 不属于企业差旅出行方式 |
| 度假产品 | 删除相关路由、工具链路和 `holiday.md` | 属于旅游线路和度假场景 |
| 打包订 | 删除相关路由、工具链路和 `package-booking.md` | 多资源组合预订不在当前 Agent 职责内 |
| OAuth 优先认证说明 | 删除 OAuth source 检查、登录和登出指引 | 避免使用本机或宿主 OAuth 身份 |
| API Key 使用说明 | 改为 Hook 注入约定，不在命令中填写 Key | 由项目按当前用户处理多用户鉴权，Skill 不接触凭证 |

Skill 当前业务边界是：酒店住宿、国内/国际航班、火车票（含高铁和动车）。不属于这些范围的旅行产品需求不调用或发现相关服务。

## 精简后的收益

1. **业务边界明确**：Agent 可见的意图和服务与企业差旅职责一致，降低旅游产品需求误路由的可能。
2. **工具选择更聚焦**：保留酒店、航班、火车三类业务及国际航线的必要分流，减少无关服务描述对模型判断的干扰。
3. **上下文更精简**：删除不使用的服务说明、调用链路和示例，减少每次加载 Skill 时的无关内容。
4. **鉴权路径一致**：Skill 不再引导 OAuth 登录或读取本机凭证；API Key 按项目 Hook 的当前用户上下文处理，避免在提示词、命令或回复中暴露密钥。
5. **维护成本更低**：后续只需维护实际使用服务的参数、边界条件和预订规则。

这些收益属于设计上的预期，应通过真实任务观察工具选择、调用次数和上下文用量；不能仅凭删除了多少文件推断 Token 或费用的具体降幅。

## 对接第三方 Skill 的经验

### 先界定项目职责，再接入能力

第三方 Skill 是通用能力包，不等于项目需求清单。接入前先明确 Agent 的用户、任务范围、可执行动作和禁止触达的业务，再逐项判断 Skill 中的意图、工具和流程是否需要保留。

### 将 Skill 内容分层审阅

建议分别检查以下部分，避免只改摘要而遗漏实际路由：

- **元数据**：名称、描述、触发词、标签和最低 CLI 版本。描述和标签会影响 Skill 是否被检索或激活。
- **意图路由**：主文件中的决策表、服务发现规则、默认行为和兜底路径。
- **工具链路**：搜索、详情、预订、取消等动作，以及是否存在副作用或需要用户确认的步骤。
- **参考文档**：逐份检查调用示例、参数约束、安全规则和场景示例。
- **认证与安全**：确认凭证由谁提供、是否按当前用户隔离，以及 Skill 是否会诱导 Agent 输出或持久化密钥。
- **包内元数据与来源信息**：区分运行时描述和上游下载、版本、摘要等来源记录，不要在无法验证来源时伪造版本或校验值。

### 删除能力时同步清理引用

移除一个服务不只是删除对应 Markdown 文件。还应检查主文件描述、标签、意图表、工具链路、服务发现条件、错误处理、通用规则和其他参考文档是否仍引用该服务。反过来，保留的业务也不能因为精简而失去必要的分流、参数真实性、日期、确认和取消约束。

### 改造认证说明时遵循真实执行链路

Skill 中的认证说明应与应用实际执行机制一致。若应用 Hook 按当前用户注入凭证，Skill 应说明凭证由 Hook 处理，不要求 Agent 读取或拼接凭证，也不应保留会触发不同身份路径的登录指引。认证失败时应按照项目实际责任边界停止并报告。

Skill 文字只是模型行为指引，不是鉴权边界。必须由 Hook、后端服务和第三方接口落实用户识别、权限校验、凭证隔离和审计；删除 OAuth 说明本身并不会实现多用户鉴权。

### 保留上游核心规则，谨慎维护分叉

只裁剪当前业务不需要的能力，保留仍在使用的服务所需的工具名、参数限制、资源 ID 来源、预订确认、取消确认和敏感信息保护规则。记录本地改动目的，并在上游 Skill 或 CLI 升级时重新对照差异，避免重要修复被覆盖，也避免将已删除的产品能力重新带回。

## 建议的接入与验证流程

1. 阅读项目内的 `AGENTS.md`、相关 Agent 注册逻辑、工具配置和已有安全设计，明确实际执行链路。
2. 列出第三方 Skill 的全部服务、触发意图、参考文件、认证方式和有副作用的操作。
3. 按“必须保留、可以删除、需要项目适配”分类，并记录每项取舍的业务依据。
4. 先修改元数据和主入口路由，再处理各参考文档及无关文件；保持必要的安全和业务约束完整。
5. 搜索已删除服务的名字、工具名、触发词和文档路径，检查失效引用与意外保留的路由。
6. 检查保留服务的调用示例和参数说明；用代表性差旅意图验证路由，并用范围外意图确认不会触发已删除服务。
7. 核对凭证处理与 Hook、后端和 CLI 的实际行为一致，检查 diff、文件状态、元数据和来源信息。
8. Skill 文档调整通常不需要 Java 编译；若同时修改了 Hook、工具注册或服务代码，则按代码变更范围补充测试和启动验证。
