# AgentScope 工具熔断与恢复机制

本文按当前项目代码说明工具熔断的实现、参数取舍、收益和失败检测/埋点约定。当前实现是项目自定义的 AgentScope Hook + Redis 状态，不是 Resilience4j 等通用熔断库。文中“当前实现”描述现状，“埋点约定”则给出后续统一观测时应遵守的口径。

## 1. 适用范围与总体流程

熔断名单目前固定为 `query_weather` 和 `query_destination_news`。两者属于目的地实时信息工具，依赖外部查询能力；预订、申请单等业务工具不在名单中。工具注册到 `tool_circuit_breaker_group` 后，`ToolCircuitBreakerHook` 才能通过工具组动态卸载或重新加入它们。

```text
PreReasoningEvent
  ├─ Redis 显示未 OPEN                         -> 确保工具在工具组中
  ├─ OPEN 且冷却未到                           -> 从工具组移除，模型不可见
  └─ OPEN 且冷却已到                           -> 加回工具组，允许一次或多次恢复探测

工具执行 -> PostActingEvent
  ├─ 结果文本包含 "Tool execution failed"       -> 失败计数 +1
  │    ├─ 普通状态下计数 > 3                   -> OPEN、递增代数、写开启时间、卸载工具
  │    └─ 冷却到期后的探测失败                 -> 重新 OPEN、增加代数、延长冷却、卸载工具
  └─ 未命中该错误前缀
       ├─ OPEN 冷却到期后的探测成功             -> 清除 OPEN 与失败计数
       └─ 普通状态成功                           -> 清除连续失败计数
```

Hook 在 `PreReasoningEvent` 维护模型可见的工具集合，在 `PostActingEvent` 根据工具结果更新 Redis 状态。它不负责自动重试工具调用；冷却结束后的下一次正常 Agent 推理会重新看到工具，工具被调用后以结果作为恢复探测。

## 2. 状态与属性设计

| 属性 | 当前设置 | 设计考量 |
| --- | --- | --- |
| 受控工具范围 | `query_weather`、`query_destination_news` | 只保护外部依赖明显、适合暂时隐藏的只读查询工具。按工具名单隔离，单个依赖故障不应影响其他业务工具。名单目前在 Hook 和 Store 中各有一份，新增/移除工具时需同步修改。 |
| 失败阈值 | 连续失败次数 `count > 3`，即第 4 次失败 OPEN | 前三次错误仍反馈给 Agent，让其有机会根据错误调整；连续成功会清零，避免把历史偶发故障累计为永久风险。代价是短时间内最多仍会有 4 次实际失败调用。阈值是代码常量，不是动态配置。 |
| 失败统计维度 | 每个工具独立 Redis key | 统计工具连续失败，而非全局失败率；一个工具的健康状态不会污染另一个工具。这里没有滑动时间窗、最小样本数或慢调用判定。 |
| 连续失败 TTL | `tool:failcount:{toolName}`，每次递增时设为 86400 秒 | 一天无新失败后计数自动消失，避免旧故障永久保留。脚本把 `INCR` 与 `EXPIRE` 放在一次 Lua 执行中，避免只增加计数却没有 TTL。 |
| OPEN 标记 | Redis Hash `tool:circuitbreaker:{toolName}`；存在 `at` 字段即视为 OPEN | 用开启时间判断 OPEN，不额外维护容易失配的布尔状态。Hash 的 `n` 保存熔断代数，`at` 保存开启时间毫秒值。 |
| 冷却时间 | `30 * 2^(n-1)` 秒，封顶 600 秒；依次为 30、60、120、240、480、600 秒…… | 反复探测失败时逐步拉长等待，降低故障依赖承受的请求压力；封顶保证不会无限期屏蔽工具。代数和开启时间由 Lua 原子更新，Hash TTL 为 86400 秒。 |
| 成功后的状态 | 普通成功清连续失败数；恢复探测成功还会删除整个 OPEN Hash | 普通成功表示连续失败链路中断；探测成功表示依赖已恢复，因此同时退出 OPEN 并清零失败计数。删除 Hash 也清除了代数，下一轮故障从 30 秒重新开始。 |
| 半开探测并发 | 未限制探测数；冷却一到，工具会在后续推理前重新可见 | 这是轻量恢复探测，便于复用 Agent 正常调用路径；但它不是严格 HALF_OPEN 状态机，同一时段多个 Agent 实例可能同时调用。高并发或有副作用的工具应增加 Redis 探测租约/信号量；当前名单是只读查询，重复探测风险较低。 |
| Redis 状态共享 | 状态存入 Redis | 多应用实例可共享失败计数与 OPEN 时间，避免各实例独立熔断。工具组修改仍发生在各自 Toolkit 上，由各 Agent 的下一次 `PreReasoningEvent` 对照 Redis 同步。 |
| AgentScope Hook | 处理 `PreReasoningEvent` 与 `PostActingEvent` | 使用 AgentScope 生命周期点，不需侵入工具实现。Pre 阶段从 ReActAgent 获取 Toolkit；无 Toolkit 时跳过并告警。Hook 只对注册该 Hook 且工具在指定组的 Agent 有效。 |

Store 中另有 `expiredTime = 11111L` 字段，但当前逻辑没有引用它；实际 TTL 均由写入处传入的 `86400` 秒决定，不能把该字段当作生效配置。

### 2.1 冷却期与 Redis 时间字段

每次进入 OPEN 时记录应用侧 `System.currentTimeMillis()`，冷却是否结束通过 `当前时间 >= at + cooldown` 判断。Redis 的 24 小时 TTL 是状态兜底清理，不代表熔断只持续一天：正常情况下冷却远早于 TTL 到期；如果服务长期无人执行且 key 被清除，工具之后按未熔断处理。

冷却时间使用“熔断代数”而非连续失败次数。普通状态下累计到阈值时进入第一代，冷却 30 秒；若恢复探测失败则代数递增并重新 OPEN。恢复成功删除 OPEN Hash，下一次新故障重新从第一代计算。

## 3. 为什么用动态工具卸载

OPEN 时从工具组 `removeTool`，使工具不再暴露给后续模型推理，避免模型在依赖持续故障期间不断选择同一工具。冷却结束后由 Hook `addTool` 恢复可见性，Agent 可以在真实业务调用中探测依赖，而不需要额外后台探活任务或单独的恢复接口。

工具组操作具备幂等检查：已经移除时不重复移除，已存在时不重复添加；操作异常会记录错误日志。熔断状态保存在 Redis，工具可见状态保存在每个 Agent 的 Toolkit，因此恢复同步是“下一次推理前执行”，不是 Redis 更新时对所有活跃 Agent 实例推送变更。

## 4. 如何判定工具执行失败

### 4.1 当前熔断判定

`ToolCircuitBreakerHook.isException` 遍历 `ToolResultBlock.output` 中的 `TextBlock`，只要任意文本包含 AgentScope 异常结果前缀 `Tool execution failed` 就认定为失败。空结果、没有文本块或其他类型内容块都不会被认定为失败。此判定发生在工具调用完成事件，不依赖日志文本或 HTTP 状态码。

需要区分以下情况：

- AgentScope 将工具抛出的异常包装为带该前缀的结果：当前会触发失败计数。
- 工具自身捕获异常并返回普通错误说明：若没有该前缀，熔断 Hook 会当作成功。
- 工具正常返回 JSON，但 JSON 中为 `"success": false`：当前熔断 Hook 不解析 JSON，因此不会计为失败。
- 业务拒绝、参数无效、资源不存在：即便结构化返回失败，也未必表示外部依赖不健康，通常不应直接计入基础设施熔断。
- 工具未注册、被其他代码拦截、超时但未以该框架错误前缀返回：不一定能由当前判定覆盖。

因此当前机制可以检测“框架包装的工具异常”，不能完整判断所有业务层失败或技术失败。特别是很多项目工具会捕获异常并返回 `{success:false,...}`；此时需要有意识地区分“业务失败”和“依赖故障”，再扩展统一识别逻辑，不能简单把所有 `success=false` 都熔断。

### 4.2 建议采用的结果约定

对需要参与熔断的工具，建议统一返回可解析的结果结构，至少包含成功标志、稳定错误码和可重试性。例如：

```json
{
  "success": false,
  "errorCode": "UPSTREAM_TIMEOUT",
  "retryable": true,
  "message": "目的地天气服务暂时无响应",
  "data": null
}
```

失败码要反映失败层次。参数校验、权限、业务规则和数据不存在等属于业务结果；连接失败、上游超时、上游 5xx、响应解析失败等通常属于依赖故障。熔断统计应只纳入约定的依赖故障类，并保留 `CIRCUIT_OPEN`、`TOOL_NOT_FOUND` 等框架/保护错误的独立类别。`retryable` 仅表达是否适合有限恢复，不允许触发无限重试。

若 AgentScope 当前工具接口以字符串返回，可将该结构序列化为 JSON 字符串，在共享的结果解析器中识别。更稳妥的长期方向是在工具边界统一产出明确的执行结果，避免各 Hook 自行猜测错误文案。兼容期内可同时识别 AgentScope 异常前缀和约定 JSON 错误码，并通过测试锁定框架版本的异常包装行为。

## 5. 约定埋点

项目已有 `AgentExecutionMonitorHook`，会记录工具开始/结束、工具名、调用 ID、耗时、结果状态和 Agent/会话/trace 标识；其当前结果状态判断也基于 `Error` / `error` 开头文本，与熔断 Hook 使用的 `Tool execution failed` 子串并非同一个口径。日志监控不能替代熔断计数，且结构化业务失败可能被现有日志标为成功。

新增或整理工具观测时，以“一次 ToolUseBlock 调用”为逻辑调用单位，执行以下约定：

1. 每次调用只产生一个最终调用计数和一个耗时观测。计时从 `PreActingEvent` 到 `PostActingEvent`，使用 `System.nanoTime()`；异常、结果缺失和熔断拒绝也必须有终态。若事件链没有产生 PostActing，应在 Agent Error/取消收尾逻辑中记录中断结果，避免只留下开始事件。
2. `success=true` 表示通过工具定义的结果协议和业务成功条件。仅仅“方法正常返回”不能算成功；结构化结果中的 `success=false` 必须按其 `errorCode` 分类。
3. 指标建议采用逻辑名：`agent.tool.calls`（计数器）、`agent.tool.duration`（耗时直方图）、`agent.tool.failures`（可选失败计数）、`agent.tool.circuit.state`（状态/转换计数）。标签只使用有限集合：`agent_code`、稳定的 `tool_name`、`result`、`error_type`、`circuit_state`。错误类型如 `BUSINESS_ERROR`、`UPSTREAM_TIMEOUT`、`UPSTREAM_5XX`、`RATE_LIMITED`、`RESULT_INVALID`、`TOOL_NOT_FOUND`、`CIRCUIT_OPEN`、`CANCELLED`、`UNKNOWN`。
4. 不把 `traceId`、会话/用户/调用 ID、原始错误消息、工具参数或结果正文放入 Micrometer 标签。它们基数高且可能包含敏感数据；需要逐次排查时写脱敏结构化日志或 trace 字段。
5. 最少保证每条工具开始/结束记录均带 `trace_id`、`agent_code`、`tool_name`、`tool_call_id`、`duration_ms`、`success`、`error_type`、`retryable`、`circuit_state`。参数只记录字段名或脱敏摘要，不记录凭证、完整个人信息或原始响应正文。
6. 区分“工具调用”与“恢复结果”：失败调用仍保留失败计数；后续 Agent 改参/换工具成功，不得把之前的失败改写为成功。可另记恢复结果，并带 `recovered=true|false`、`recovery_action`（如 `retry`、`fallback`、`user_input`）和稳定错误类别。
7. 熔断状态变更记录 `CLOSED/AVAILABLE -> OPEN`、`OPEN -> PROBE_ALLOWED`、探测成功恢复、探测失败重开及冷却秒数。当前代码的“半开”只是工具重新可见，埋点名称最好写 `probe_allowed`，不要暗示存在并发探测限额。

建议监控调用量、失败率、P95/P99 耗时、依赖错误类别、OPEN 次数/持续时间和探测成功率。失败率告警应设置最小调用量；低流量工具的一次错误不宜触发持续告警。指标名、直方图桶和告警阈值应按项目当前 Micrometer/Prometheus 配置与工具 SLA 落地。

## 6. 收益与边界

当前机制的收益是：依赖短时故障时可让 Agent 在少数失败后停止重复暴露该工具；按工具隔离，其他 Agent 工具仍可工作；Redis 共享状态使多个应用实例看到相同 OPEN 冷却；指数退避能降低故障恢复期间的探测压力；冷却到期后通过真实工具调用自动恢复，无需人工清状态或后台探活。

边界也需要保留在运维预期中：失败检测依赖特定错误文本前缀；阈值、冷却参数和工具名单目前硬编码；没有滑动窗口、慢调用熔断和 HALF_OPEN 并发配额；工具组可见性只在每轮推理前校准；多实例 Toolkit 状态不是实时推送；Redis 不可用时当前 Hook/Store 没有明确的降级策略。因此对重要外部依赖，应先统一错误协议与埋点，再考虑把名单和参数配置化、增加探测租约与 Redis 故障处理。

## 7. 代码定位

- `src/main/java/cn/lwccxy/trip/agent/hooks/ToolCircuitBreakerHook.java`：Hook 事件处理、失败识别、阈值与工具组卸载/恢复。
- `src/main/java/cn/lwccxy/trip/agent/store/toolcircuitbreaker/ToolCircuitBreakerStore.java`：Redis key、原子计数、冷却计算与 OPEN 状态。
- `src/main/java/cn/lwccxy/trip/agent/hooks/AgentExecutionMonitorHook.java`：Agent 和工具生命周期耗时/结果日志观测。
- `src/main/java/cn/lwccxy/trip/agent/tools/DestinationLiveTools.java`：受控目的地实时信息工具。
- `src/main/java/cn/lwccxy/trip/agent/GeneralInfoAgent.java`、`src/main/java/cn/lwccxy/trip/agent/ItineraryPlanningAgent.java`：工具组注册和熔断 Hook 接入位置。
