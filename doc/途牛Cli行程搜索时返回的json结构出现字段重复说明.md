## 如果不做精简会有什么问题
精简前整个json结构进入模型上下文产生的token以及费用如下，这里是拿qwen3.5模型去做测算
token数量：大约16,450
字符数量：45,126

大约1.6w个token进入模型的上下文, 而且还是json结构, 这样模型会很容易传错搜索回来的行程。以及搜索结构还会随着Agent轮次的增加一直携带下去。
假如Agent推理了1轮, 就是1.6wToken。推理持续进行到了10轮就是16w的token。这是一笔昂贵的开销。

## 精简后
token数量：大约8k
字符数量：2w

直接节省了一半的上下文, 以及token的费用开销

## 解决方案

在行程规划 Agent 中注册 `TuniuSearchResultHook`，利用 AgentScope 1.0.12 的 `PostActingEvent` 在命令工具执行完成后精简结果。Hook 只处理以下途牛搜索命令：

- 航班：`tuniu call flight searchLowestPriceFlight`
- 火车/高铁：`tuniu call train searchLowestPriceTrain`
- 酒店：`tuniu call hotel tuniuHotelSearch`

搜索命令可能带有参数，也可能由鉴权 Hook 在前面注入 `TUNIU_API_KEY` 环境变量；这些形式都会识别。航班详情、火车查询详情、酒店详情和下单等其他命令不在精简范围内。

对于命令行工具的标准输出，Hook 会将其解析为 JSON，并检查 `result.structuredContent` 是否存在，同时确认 `result.content` 中至少有一个非空的 `type: "text"` 文本块。满足这两个条件时，删除 `result.structuredContent`，保留 `result.content`、外层元数据和其余字段。这样保留的是完整的文本结果数组，不要求结果一定只有 `content[0]` 一个文本块。

结果替换分为两处：

1. 用精简后的文本块重建 `PostActingEvent` 中的 `ToolResultBlock`，保留工具调用标识、工具名称、元数据及其他输出块。
2. AgentScope 1.0.12 在触发完成 Hook 前已经生成了供后续推理和记忆使用的 `toolResultMsg`。Hook 会一并替换该消息中的对应工具结果块，并保留消息标识、时间、元数据及其他内容，因此下一轮模型实际读取和保存的都是精简后的结果。

若输出不是完整 JSON、JSON 解析失败、缺少 `structuredContent`，或 `content` 中没有可保留的非空文本，Hook 会原样保留结果，避免破坏错误输出或仅有结构化数据的响应。命令工具原有的退出码、标准错误和外围文本也会保留。

每次成功精简时，Hook 会输出一条 `[途牛搜索结果精简审计]` 日志，记录工具调用 ID、精简前字符数、精简后字符数和节省字符数。字符数按工具结果中所有文本输出块的 Unicode 码点累计，包含命令工具的退出码、标准输出/错误标记及其文本；日志不包含原始命令、参数或搜索结果内容。该字符数用于观察结果体积变化，不等同于模型 Token 数。

实现位置：`src/main/java/cn/lwccxy/trip/agent/hooks/TuniuSearchResultHook.java`；注册位置：`ItineraryPlanningAgent` 的 Hook 列表。
