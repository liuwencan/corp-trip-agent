# AutoContextMemory 六级渐进式上下文压缩说明

## 1. 结论与适用范围

本文依据当前 `CorpTripAgent` 的依赖版本 `io.agentscope:agentscope:1.0.12`，结合该版本 `AutoContextMemory`、`AutoContextConfig`、`AutoContextHook` 的实际实现整理。项目中的 MasterAgent、GeneralInfoAgent、ItineraryPlanningAgent、BookingAgent、OrderManagementAgent 使用 `AutoContextMemory`；配置均调用默认 `AutoContextConfig.builder().build()`，并将 Agent 的主模型传给压缩器。

“六级渐进式压缩”是六种按成本和信息保真度递进的策略，不是每次压缩都把六级全部跑一遍。每次推理前，框架先看是否达到压缩门槛；达到后依次尝试策略 1 到 6，某级成功就更新工作记忆并立即返回。下一轮推理前若仍超限，再重新触发。因此通常先用较局部、低破坏性的办法，逐级扩大处理范围。

## 2. 什么时候触发

每次 `PreReasoningEvent` 到来时，`AutoContextHook` 调用 `memory.compressIfNeeded()`。默认配置的触发条件是以下任一成立：

| 条件 | 默认值 | 含义 |
|---|---:|---|
| 工作记忆消息数 | 100 条 | 消息数达到 100 即触发 |
| 工作记忆估算 Token 数 | 98,304 Token | `maxToken=131,072`，乘 `tokenRatio=0.75` 后得到阈值 |

Token 数由框架的 `TokenCounterUtil` 估算，不应视为模型服务返回的精确 Token 用量。项目没有覆写这些默认值。

## 3. 六级策略

### 第 1 级：压缩较早轮次的工具调用组

- **处理对象：** 最近保留窗口之前、属于较早推理轮次的一组工具调用与结果消息。工具消息需连续达到默认 `minConsecutiveToolMessages=6` 条，且会避开被识别为 Plan 状态的工具调用。
- **怎么压：** 将被选中的工具调用组交给压缩提示词整理成较短的调用/结果摘要，替换工作记忆中的原消息。实现会扫描多个候选组，最多连续处理 5 组；一次策略调用成功后即停止本轮六级流水线。
- **需要 LLM：** 是，使用传入的 Agent 主模型生成摘要。
- **为什么优先做：** 工具结果通常重复、冗长，但对后续推理仍需保留“做过什么、得到什么结果”。先归并成摘要，较原样保留完整工具轨迹节省上下文，同时不必改写整段对话。

### 第 2 级：卸载较早轮次的大消息，保护最近 50 条

- **处理对象：** 达到默认 `largePayloadThreshold=5,120` 字符/长度门槛的大消息，通常是工具结果；扫描较早轮次，并跳过最近 `lastKeep=50` 条消息。
- **怎么压：** 不生成语义摘要，而是将原消息完整保存到 AutoContextMemory 的卸载存储中，在上下文消息中留下短预览和 `CONTEXT_OFFLOAD` UUID 标记。需要原文时可通过自动注册的 `context_reload` 工具取回。
- **需要 LLM：** 卸载和替换本身不需要 LLM。只有 Agent 后续决定调用 `context_reload` 时，正常 Agent 推理才可能涉及模型；工具取回本身不负责摘要。
- **为什么这样做：** 大块输出常需要保留可追溯的完整原文，但每轮都放进上下文成本太高。卸载减少常驻 Token，同时把原文保存在可恢复的位置；保留尾部窗口避免过早处理刚产生、最可能仍相关的内容。

### 第 3 级：卸载较早轮次的大消息，不再保护最近窗口

- **处理对象：** 与第 2 级相同，但取消 `lastKeep` 对最近消息的保护。
- **怎么压：** 同样将完整消息卸载，工作记忆中保留预览和恢复标记，不做语义摘要。
- **需要 LLM：** 否。
- **为什么需要这一层：** 第 2 级因消息仍在最近 50 条而找不到目标时，允许处理这些近期大块内容，避免“最近窗口保护”使超长内容一直无法释放。它比删除原文更保守，因为仍可按 UUID 取回。

### 第 4 级：总结较早轮次的对话

- **处理对象：** 最近推理轮次之前、可形成完整历史片段的普通对话消息。
- **怎么压：** 将早期对话片段作为输入，用专门的历史对话总结提示词生成一条摘要消息，替代这段原消息；较新的消息继续保留。
- **需要 LLM：** 是，使用 Agent 主模型。
- **为什么放在卸载之后：** 对话通常包含意图、约束、确认和结论等语义关系，简单截短容易破坏意思。只有前面针对工具组和超大消息的局部策略无效时，才用模型总结更大范围的历史。

### 第 5 级：总结并卸载当前轮次的大消息

- **处理对象：** 当前推理轮次中的大消息。当前轮内容可能还没有进入“较早轮次”策略的候选范围。
- **怎么压：** 提取大消息内容交给模型生成摘要，同时把完整原消息卸载保存；上下文里放摘要及恢复标记，兼顾简要可读与原文可恢复。
- **需要 LLM：** 是，摘要需要 Agent 主模型；保存原文及插入引用不需要额外模型调用。
- **为什么需要这一层：** 当前轮产生的大型结果可能马上影响下一轮决策，单纯只留预览会损失关键结论，因此先摘要后卸载；完整内容仍可按需恢复。

### 第 6 级：总结当前轮次消息

- **处理对象：** 当前轮次的消息整体，是本轮流水线覆盖面最大的一层。
- **怎么压：** 使用当前轮总结提示词把该轮消息合并为一条较短摘要，替代原消息集合。
- **需要 LLM：** 是，使用 Agent 主模型。
- **为什么最后执行：** 该层会把多条当前轮内容收敛成摘要，信息损失风险高于前面的工具组归并和原文卸载，所以留到最后作为兜底。摘要保留当前轮主要过程和结果，避免因为局部策略均无法降低上下文而继续无限累积。

## 4. 默认参数与实际影响

| 参数 | 默认值 | 作用 |
|---|---:|---|
| `largePayloadThreshold` | 5,120 | 大消息候选阈值 |
| `maxToken` | 131,072 | Token 压缩基准上限 |
| `tokenRatio` | 0.75 | 按基准上限的 75% 触发，即 98,304 Token |
| `offloadSinglePreview` | 200 | 大消息卸载后保留的预览长度配置 |
| `msgThreshold` | 100 | 消息数触发阈值 |
| `lastKeep` | 50 | 第 2 级扫描时保护的尾部消息数；第 3 级不保护 |
| `minConsecutiveToolMessages` | 6 | 第 1 级识别可压缩工具消息组的最小连续条数 |
| `currentRoundCompressionRatio` | 0.3 | 当前轮摘要长度目标相关配置 |
| `minCompressionTokenThreshold` | 5,000 | 避免压缩收益太低时执行部分总结策略 |

上述数字是 `1.0.12` 默认值；当前业务 Agent 未显式设置。阈值作用于框架认定的候选对象，并非保证每次都会压缩或最终 Token 一定低于阈值。策略可能因无合格目标、收益不足等原因跳过，之后继续试下一层；六层都失败时会记录警告，本次不做强制截断。

## 5. LLM 调用和成本

第 1、4、5、6 级涉及模型生成摘要；第 2、3 级是本地消息筛选、卸载、占位符替换，不需要 LLM。使用的模型就是创建 `AutoContextMemory` 时传入的 `model`，本项目目前传 Agent 主模型，没有配置单独的轻量压缩模型。

压缩 LLM 调用会产生额外延迟和输入/输出 Token。项目的 `AgentExecutionMonitorHook` 监听 `PreSummaryEvent` / `PostSummaryEvent` 并记录压缩耗时、摘要长度及 `ChatUsage`。但它主要展示压缩总结事件；第 2、3 级纯卸载没有摘要模型调用，不应期待同样的模型 Token 记录。

## 6. 与项目其他机制的边界

- `AutoContextMemory` 的摘要/卸载管理的是当前 Agent 的工作上下文。卸载内容保存在该内存模块中，可由 `context_reload` 恢复。
- `ItineraryPlanningAgent` 配置的长期记忆是另一套跨会话机制，基于 `LongTermMemory` / Mem0；它不是六级压缩的一部分。
- `SkillContentCollapseHook` 针对重复出现的 Skill 正文做确定性折叠，解决正文加载后在短期窗口内重复占上下文的问题。它与 AutoContextMemory 的阈值驱动压缩互补。
- 行程候选数据由专用 Store/工具保留，规划提示也要求通过工具重新加载完整候选，不应依赖可能被摘要的对话记忆。这是业务数据正确性的保护措施。

## 7. 如何观察运行时实际命中哪一级

AgentScope 在压缩时会输出 `Strategy 1` 至 `Strategy 6` 的 applied/skipped 日志，可据此确认命中的层级。项目的 `AgentExecutionMonitorHook` 额外记录压缩开始/结束、待压缩消息数、耗时和模型 Token。对比这些日志与 Agent 实际输入，可以判断压缩是否触发、是否只做了无 LLM 卸载，以及摘要后是否仍有大量历史消息。

## 8. 一句话概括

AutoContextMemory 的思路是：先归并旧工具轨迹，再卸载可恢复的大块原文（先保护近期、再放宽保护），然后才用模型概括旧对话、当前大消息和当前轮整体；每次只执行第一个可用策略，以尽量低的信息损失逐步释放上下文。
