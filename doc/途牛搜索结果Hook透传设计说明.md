# 途牛搜索结果 Hook 透传设计说明

## 1. 背景

行程规划智能体会通过 `execute_shell_command` 调用途牛 CLI，搜索航班、火车票和酒店。搜索结果通常是包含多层包装的 JSON，既有 `result.content[].text` 中的业务文本，也可能有内容重复的 `structuredContent`。

如果把完整搜索结果直接交给大模型，再要求大模型把结果复制到后续工具的参数中，搜索结果就会经历一次不必要的“模型中转”。本项目采用 `PostActingEvent` Hook 捕获工具结果，在 `TuniuSearchResultHook` 精简结果之后，把候选方案直接写入 Redis Hash。后续工具按当前用户和行程条件读取 Redis，结果传递由程序完成，不依赖大模型复述 JSON。

相关实现：

- 精简 Hook：`src/main/java/cn/lwccxy/trip/agent/hooks/TuniuSearchResultHook.java`
- 捕获 Hook：`src/main/java/cn/lwccxy/trip/agent/hooks/TuniuSearchResultCaptureHook.java`
- Redis 存储：`src/main/java/cn/lwccxy/trip/agent/tools/store/TuniuSearchCandidateStore.java`
- 注册位置：`ItineraryPlanningAgent` 的 Hook 列表

## 2. 两种传递方式

### 2.1 让大模型中转结果

链路如下：

```text
途牛搜索工具
    -> 完整结果进入模型上下文
    -> 大模型读取、理解并重新组织结果
    -> 大模型把候选 JSON 或候选字段填入后续工具参数
    -> 后续工具继续处理
```

这种方式把大模型同时当成推理器、序列化器和数据搬运器。模型需要从长 JSON 中识别候选、记住字段、保持数组完整，并在下一次工具调用时重新生成结构。

### 2.2 Hook 捕获并程序透传

链路如下：

```text
途牛搜索工具
    -> TuniuSearchResultHook 精简重复结构
    -> TuniuSearchResultCaptureHook 解析业务 JSON
    -> 按用户写入 Redis Hash
    -> 后续工具按用户和行程条件读取 Redis
    -> 程序直接把候选传给业务逻辑
```

模型仍然可以看到精简后的结果或摘要，用于向用户解释和做决策；但后续工具使用的候选原文由 Redis 保存和读取，不要求模型再次复制。

## 3. 为什么使用 Hook 捕获

### 3.1 Hook 位于工具结果和下一轮推理之间

`PostActingEvent` 能拿到工具调用参数和工具结果。捕获 Hook 的优先级为 `30`，`TuniuSearchResultHook` 的优先级为 `20`，因此捕获发生在结果精简之后。这样可以同时满足两个目标：

1. 降低进入模型上下文的重复内容。
2. 将同一份精简后的业务 JSON 保存为后续工具可读取的数据源。

Hook 不修改 Agent 的主流程返回值。Redis 写入失败或解析失败时，只记录告警并放行原始事件，避免候选缓存故障阻断对话。

### 3.2 Hook 能保留工具调用上下文

捕获时仍能读取：

- 工具调用 ID，用于审计和排查。
- 原始 Shell 命令，用于识别搜索类型和解析 `-a` 参数。
- 当前 Reactor 上下文中的用户 ID，用于用户隔离。
- 精简后的工具结果，用于解析候选方案。

这些信息在工具结果离开执行链后再交给模型，可能需要额外约定或重新拼装；Hook 直接处于正确的生命周期位置，能够一次完成归属、解析和存储。

## 4. Redis Hash 存储设计

### 4.1 用户隔离

每个用户使用独立 Redis Hash：

```text
tuniu:search:candidates:{用户 ID 的 URL-safe Base64 编码}
```

用户 ID 经过编码后再拼入 Key，避免特殊字符导致 Key 冲突。搜索结果不会通过共享字段或全局变量保存，避免并发会话串数据。

### 4.2 Hash Field

Hash Field 表示一次搜索条件：

```text
flight_北京_上海_2026-12-01
train_北京_上海_2026-12-01
hotel_上海_2026-12-01_2026-12-03
```

Field 中的城市和日期来自途牛 CLI 的 `-a` JSON 参数。缺少参数时使用 `unknown`，保证异常输入不会生成空 Field。

### 4.3 Hash Value

Value 是 JSON 字符串，包含搜索类型、查询参数和候选数据：

```json
{
  "type": "flight",
  "args": {
    "departureCityName": "北京",
    "arrivalCityName": "上海",
    "departureDate": "2026-12-01"
  },
  "data": {
    "data": [
      {
        "flightNumber": "MU1234",
        "departureTime": "2026-12-01 08:00"
      }
    ]
  }
}
```

Redis Hash 默认保留 24 小时。相同查询条件再次搜索时，程序会合并候选并去重：航班使用航班号和出发时间，火车使用车次和出发时间，酒店优先使用酒店 ID，其次使用酒店名称。新结果覆盖相同业务标识的旧结果。

后续工具可以通过 `loadByTrip` 一次读取去程交通、返程交通和酒店候选，使用 `HMGET` 直接取得多个 Field，不需要模型携带或重建候选 JSON。

## 5. 这样做的好处

### 5.1 降低 Token 和调用成本

途牛搜索结果通常包含大量字段、分页信息和嵌套结构。若每一轮都让模型读取并继续携带完整结果，结果会随着 Agent 轮次重复进入上下文。Hook 先删除重复结构，Redis 保存候选，后续工具读取时不需要再次把完整 JSON 放进模型输入，可以显著降低上下文长度和模型调用费用。

### 5.2 避免模型复制造成的数据错误

模型适合做筛选、解释和决策，不适合可靠地搬运长数组。让模型重新生成工具参数时，可能出现：

- 漏掉某些候选项。
- 复制错航班号、车次、价格或时间。
- 改变字段名称、数据类型或嵌套层级。
- 把多个搜索结果混在一起。
- 生成看似合法但无法追溯到原始搜索的内容。

Redis 透传保存的是程序实际解析到的候选数据，后续工具拿到的字段不会经过模型改写。

### 5.3 保持跨轮次和跨工具的一致性

搜索、筛选、排序、生成行程和后续下单可能分布在多个 Agent 轮次。把候选放在用户隔离的 Redis Hash 中，后续工具可以按同一 Field 读取同一批数据，避免依赖模型记忆上一轮的文本内容。

### 5.4 支持重复搜索和结果更新

同一日期和路线可能被重复搜索。Store 可以按业务唯一标识合并结果，并以最新结果覆盖旧候选。这样既避免重复项堆积，也能反映价格、余票和酒店库存的最新状态。

### 5.5 更容易审计和排查

Hook 可以记录工具调用 ID、用户归属、搜索类型、Hash Field 和候选数量，而不必把完整行程数据写入日志。出现“工具使用了错误候选”时，可以根据用户和查询条件检查 Redis 中的原始缓存条目。

### 5.6 降低敏感数据暴露面

完整候选数据不需要在模型提示词、模型输出或工具参数中反复出现。模型上下文只保留完成推理所需的摘要或精简结果，详细候选留在受应用控制的 Redis 中，有利于减少日志、Tracing 和第三方模型侧的重复暴露。

## 6. 如果不这样做会发生什么

### 6.1 上下文持续膨胀

一次搜索结果可能有数千到数万字符。Agent 每多推理一轮，就可能再次携带工具结果。长结果会挤占模型上下文窗口，导致后续指令、用户约束和系统规则可用空间减少。

### 6.2 成本随轮次放大

搜索结果每次被模型读取都要计算输入 Token。若结果在 10 轮推理中重复出现，成本大致按重复次数放大，而实际业务只需要保存一次并复用。

### 6.3 候选传递不可控

大模型可能因为上下文截断、注意力分散或输出限制而只传递部分候选。后续工具即使成功执行，也可能只处理了模型挑出的少数数据，无法确认是否遗漏了更优方案。

### 6.4 数据会被模型改写

模型在生成 JSON 时可能进行格式化、摘要或推断。对价格、时间、余票、酒店 ID 等字段来说，即使只改动一个字符，也可能导致后续查询、比价或下单关联错误。

### 6.5 多次搜索容易串结果

用户先搜索北京到上海，再搜索上海到北京时，模型上下文中可能同时存在两组相似候选。依靠模型从自然语言和长 JSON 中选择正确的一组，容易发生去程、返程或酒店条件混用。

### 6.6 可靠性依赖模型输出格式

后续工具必须假设模型会始终输出合法 JSON、完整数组和正确字段。一旦模型输出被截断、包裹在 Markdown 代码块中或混入解释文本，工具还需要增加大量容错解析，仍无法保证数据完整。

### 6.7 难以建立确定性的权限边界

如果候选方案完全通过模型参数传递，服务层很难判断这些数据是否确实属于当前用户、是否来自当前搜索、是否已经过期。Redis Key 按用户隔离后，工具可以在读取层强制执行归属约束，不接受模型传入的任意用户数据。

## 7. 设计边界

Hook 透传不是让模型完全看不到搜索结果。模型仍可以读取精简后的结果，用于解释、排序偏好和询问用户；Redis 负责保存需要准确传递的权威候选数据。两者职责应保持分离：

| 组件 | 主要职责 |
| --- | --- |
| 大模型 | 理解用户意图、比较候选、解释取舍、决定调用哪个工具 |
| `TuniuSearchResultHook` | 删除重复结构，控制进入模型上下文的数据体积 |
| `TuniuSearchResultCaptureHook` | 在结果完成后识别、解析并按用户保存候选 |
| `TuniuSearchCandidateStore` | 通过 Redis Hash 提供用户隔离、合并、读取和清理 |
| 后续业务工具 | 按当前用户和行程条件读取候选，并执行确定性的业务处理 |

Redis 候选缓存应设置合理 TTL，并在价格、库存或余票敏感的操作前重新确认实时状态。缓存用于可靠传递搜索结果，不代表供应商状态永久有效，也不能绕过最终的权限、价格和库存校验。

## 8. 结论

Hook 捕获加 Redis Hash 透传的核心价值，是把“模型推理”和“业务数据搬运”分开。模型负责理解和决策，程序负责保存、归属、去重和精确传递候选数据。这样可以减少上下文和费用，避免长 JSON 被模型改写或截断，并让后续工具获得可追溯、可校验、按用户隔离的候选方案。
